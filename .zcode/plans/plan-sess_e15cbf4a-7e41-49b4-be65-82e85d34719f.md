# AI Data Pilot — план развития

## Контекст (после аудита кода)

Проект зрелее, чем типичный WIP: декаплированная архитектура (FastAPI + React 19/Vite), 2 агента, 5 LLM-провайдеров, дашборд, деплой на HF Spaces. Но есть **4 критичных слабых места**, которые подрывают и демо, и ценность для собеседования:

1. **`oleg.py:203-205`** — голый `except Exception: plan = _mock_plan(...)` → при любой SQL-ошибке пользователь видит «правдоподобные» mock-данные без предупреждения. На демо можно показать неверные цифры и не заметить.
2. **Нет self-correction** — агент не видит ошибку SQL и не пробует снова.
3. **`ANSWER_SYSTEM` просит «тренды/аномалии»**, но в промпт передаётся сырой JSON таблицы → модель считает проценты «в голове» и ошибается.
4. **`registry.py:94`** — молчаливый fallback на Mock → собеседующий не понимает, что реальная модель не задействована.

## Приоритизация (ваш выбор: все 4 направления + обе цели)

Реализовать всё сразу = распылиться и сломать демо. Поэтому **roadmap из 3 фаз**, с **Фазой 1 в этой сессии**:

## ФАЗА 1 — Надёжность + Аналитика (реализуем сейчас)

### 1.1. Self-correction loop для Олега
**Файл:** `backend/app/agents/oleg.py` (новая функция `_plan_with_correction`)

Сейчас: `run_sql` упал → молча подмена на mock.
Будет: `run_sql` упал → ошибка возвращается в LLM с инструкцией «исправь SQL, вот ошибка: …» → до **2 попыток**. Если все попытки провалились → **явное** сообщение пользователю «Не смог построить запрос. Вот что модель попыталась сделать» + показываем ошибку. Mock-fallback **только для demo-режима** (`provider.provider == "mock"`), и тогда честно помечаем ответ как демонстрационный.

```python
# Псевдокод нового flow
plan = await _generate_plan(provider, question)  # LLM или mock
for attempt in range(MAX_ATTEMPTS := 3):
    try:
        result = run_sql(engine, plan["sql"])
        break
    except SqlGuardError as e:
        # ошибка валидации — не переспрашиваем, показываем
        return _error_response(plan, e)
    except Exception as e:
        if provider.provider == "mock" or attempt == MAX_ATTEMPTS - 1:
            # в demo-режиме или после всех попыток — честная ошибка
            return _error_response(plan, e, attempted=True)
        plan = await _repair_plan(provider, question, plan["sql"], str(e))
# если все попытки провалились — result остаётся None
```

**Архитектурное решение:** отказываемся от молчаливого `_mock_plan` при сбоях реальной модели. Mock-данные остаются только когда пользователь сам выбрал demo-режим. Это главное для доверия на демо.

### 1.2. Аналитический слой на Python
**Новый файл:** `backend/app/core/analytics.py`

Принцип: **LLM не считает цифры — она оформляет текст по готовым метрикам.**

Python анализирует результат SQL и вычисляет:
- **Детекция временного ряда** — первая колонка похожа на дату (`date`/`timestamp`/строка ISO) → тренд.
- **Сравнение периодов** — если рядом есть «предыдущий период» (двойная колонка current/previous или возможность пере-выполнить SQL со сдвигом) → MoM/WoW/YoY в %.
- **Топ-N и аутсайдеры** — сортировка по числовой колонке, выделение топ-3 и худших.
- **Аномалии** — z-score по числовому ряду, флаг значений |z| > 2 как «выброс».
- **Сводные метрики** — sum/avg/min/max/медиана по числовым колонкам, доля пустых.

На выходе — структура `Insights`:
```python
{
  "is_timeseries": True,
  "trend_direction": "up" | "down" | "flat",  # по линейной регрессии
  "trend_pct": 12.4,
  "top": [{"label": "Москва", "value": 45000, "share": 0.32}, ...],
  "outliers": [{"label": "Сочи", "value": 120, "z": -2.3}],
  "summary": {"col": {"sum": ..., "avg": ..., "min": ..., "max": ...}},
  "highlights": [  # готовые «факты» для LLM-текста
    "Выручка выросла на 12.4% за период",
    "Топ-1: Москва (32% от общей выручки)",
    "Аномалия: Сочи (значение ниже ожидаемого, z=-2.3)",
  ]
}
```

### 1.3. Новый промпт ответа с готовыми инсайтами
**Файл:** `backend/app/agents/oleg.py` — пересобрать `ANSWER_SYSTEM`

Старый промпт: «дай тренды, топы, аномалии» (модель сама считает).
Новый промпт: «Вот готовые факты (highlights). Оформи их коротким деловым ответом на языке вопроса. Не выдумывай цифры вне этого списка. Если фактов мало — скажи, что данных недостаточно.»

В `table_preview` добавляем поле `"insights": insights_dict`.

**Эффект:** цифры в ответе всегда точные (считает Python), а LLM занимается тем, в чём хороша — связным текстом на нужном языке. На собеседовании это killer-аргумент: «Я не доверяю LLM считать проценты, поэтому метрики считает детерминированный слой».

### 1.4. Явные статусы ответа (прозрачность для демо)
**Файлы:** `backend/app/schemas/dto.py`, `frontend/src/components/ResultCard.tsx`, `frontend/src/lib/api.ts`

Добавить поле `status: "ok" | "demo" | "partial" | "error"` и опционально `warnings: string[]` в ответ Олега:
- `ok` — реальная модель, SQL выполнен, инсайты посчитаны.
- `demo` — выбран demo-режим, данные детерминированные mock.
- `partial` — real-модель, но SQL упал и выполнен mock/fallback (помечаем честно).
- `error` — не удалось выполнить запрос.

В `ResultCard` — компактный бейдж статуса (зелёный/жёлтый/серый/красный) рядом с методологией. Это снимает главный риск: на демо всегда видно, реальный ли это ответ.

### 1.5. Применить `sql_timeout_sec` (объявлен, но не использовался)
**Файл:** `backend/app/core/sql_guard.py`

`config.py:35` задаёт `sql_timeout_sec = 8.0`, но `run_sql` его не применяет. Добавить таймаут через `engine.connect()` с `connection.exec_driver_sql("PRAGMA ... ")` не подойдёт для всех СУБД в будущем, поэтому для SQLite — мягкий таймаут через `concurrent.futures.ThreadPoolExecutor` + `future.result(timeout=...)`, чтобы не зависнуть на тяжёлом запросе. В случае таймаута — возвращаем как `partial`/`error` (см. 1.4), а не молчим.

### 1.6. Убрать молчаливый fallback провайдера в реальном режиме
**Файл:** `backend/app/llm/registry.py:89-96`

Сейчас: `get_provider("openai:gpt-4o")` без ключа → тихо возвращает `MockProvider`. Это маскирует проблему.
Решение: разделить `get_provider` (для чата — текущее поведение сохраняем как soft-fallback, чтобы демо не падало) и `get_provider_strict` (для внутренней логики — кидает ошибку, если ключа нет). В UI `App.tsx:103-107` уже фильтрует по `available`, так что пользователь видит ○/● — это достаточно. Но в `ResultCard` добавить явный бейдж demo-режима (см. 1.4), чтобы ответ был честно помечен, даже если выбран реальный провайдер, но сработал fallback.

4. Тяжёлый запрос не вешает endpoint дольше `sql_timeout_sec`.
