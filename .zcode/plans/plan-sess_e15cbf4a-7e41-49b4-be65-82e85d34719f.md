# Agent Loop (ReAct) — план

## Контекст

Превращаем Олега из линейного flow в настоящего агента: для сложных вопросов (сравнения, «почему», тренды) LLM сама решает, какие tools вызвать и в каком порядке, видит результаты, продолжает. Простые вопросы остаются на быстром линейном path.

**Решения пользователя:**
- Tool calling: **prompt-based** (универсальный, работает со всеми провайдерами + Mock)
- Объём: **гибрид** — простой→линейно (текущий `run_oleg_streaming`), сложный→loop
- Демо-сценарий: **сравнение периодов** («Почему выручка упала в июле?»)

## Архитектура

### Router: что считать «сложным» вопросом
В начале `run_oleg_streaming` классифицируем вопрос через тот же LLM-вызов (или простую эвристику для Mock):
- **Простой** (1 SQL): «покажи выручку по регионам», «топ городов» → текущий линейный flow
- **Сложный** (multi-step): содержит «почему», «сравни», «причины», «динамика», «упало/выросло», явное сравнение периодов → Agent Loop

Эвристика для Mock (без LLM): ключевые слова `почему|сравни|причин|динамик|упал|вырос|изменен`. Для реальной модели — короткий классификатор-промпт. Это дешёвый вызов, не добавляет заметной задержки.

### Tool-набор (5 инструментов)
```
database_query(sql)         → {columns, rows, row_count}   (через sql_guard)
calculate(expression, data) → {result}                      (проценты, рост, среднее)
analyze(data)               → {highlights, outliers, trend} (analytics.py)
create_chart(type, x, y)    → {chart}                       (_build_chart)
finish(answer)              → завершает loop, answer = финальный текст
```

`finish` — это явный сигнал «я готов ответить». Без него loop ограничен `MAX_LOOP_STEPS = 6`.

### Prompt-based tool-calling контракт
Системный промпт описывает tools и требует ответ в виде:
```json
{"thought": "краткое рассуждение", "tool": "database_query", "args": {"sql": "SELECT ..."}}
```
или
```json
{"thought": "нашёл причины", "tool": "finish", "args": {"answer": "Выручка упала на 8.4%..."}}
```

История диалога передаётся через `messages`:
- `user`: исходный вопрос
- `assistant`: предыдущие `{thought, tool, args}` (строкой)
- `user` (role="tool"): результат предыдущего tool-call (JSON строкой)

### Mock-совместимость (критично для демо)
Mock-провайдер не умеет tool-call'ить. Решение: **scripted mock loop** — для demo-режима срабатывает детерминированный сценарий сравнения периодов (запрос июня → запрос июля → вычисление дельты → анализ → finish). Это тот же паттерн, что `_mock_plan` — но последовательность шагов. Каждый шаг эмитится в trace, пользователь видит «настоящий» multi-step процесс.

### ReAct loop (функция `_run_loop`)
```
messages = [user_question]
for step in range(MAX_LOOP_STEPS):
    emit step "Агент размышляет" (running)
    decision = await provider.complete(LOOP_SYSTEM + tools_desc, messages)
    parsed = parse_json(decision)
    if parsed.tool == "finish":
        emit step done "Финальный ответ"
        return answer
    emit step "Вызываю: {tool}" with args (done)
    tool_result = dispatch_tool(parsed.tool, parsed.args)
    emit step "{tool} → {summary}" (done with detail)
    messages.append(assistant=decision)
    messages.append(tool=tool_result)
emit step error "Превышен лимит шагов"
return error
```

### Frontend
Без изменений — AgentTrace уже умеет рендерить произвольный список шагов, шаги loop'а (`database_query`, `calculate`, `analyze`, `finish`) лягут в тот же компонент. SSE-контракт не меняется.

### Что НЕ делаем

- ❌ Изменения фронтенда (trace уже достаточно)

## Демо-сценарий: «Почему выручка упала в июле?»

В demo-режиме (mock) сработает scripted loop:
1. `database_query` — выручка по месяцам (июнь, июль) ✓
2. `calculate` — изменение: «-8.4%» ✓
3. `database_query` — поездки по месяцам ✓
4. `calculate` — изменение поездок ✓
5. `analyze` — инсайты ✓
6. `finish` — «Выручка упала на 8.4%. Основной фактор — снижение количества поездок в двух крупнейших регионах.»

С реальной моделью — LLM сама пройдёт похожий путь через prompt-based tool-calling.

## Критерии готовности
1. Вопрос «Почему выручка упала в июле?» в demo-режиме → multi-step trace (≥4 шагов) + финальный текст с цифрами.
2. Вопрос «Топ городов» → по-прежнему линейный flow (1 planner + 1 database_query + ...), быстро.
3. С реальной моделью (через fake-провайдер в тестах) — loop доходит до `finish`.
4. Лимит `MAX_LOOP_STEPS` срабатывает честно (не бесконечный loop).
5. Все 76 существующих тестов остаются зелёными.
6. Фронтенд рендерит loop-шаги без изменений.

## Риск-митигация
- **Гибрид** = если loop сломается, простые вопросы всё равно работают
- **Scripted mock loop** = демо надёжно работает offline (главный риск native tool-calling — mock не умеет)
- **MAX_LOOP_STEPS + таймаут** = защита от бесконечного цикла
- **Линейный flow не трогаем** = откат = просто вернуть router на "всегда linear"
