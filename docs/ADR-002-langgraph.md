# ADR-002: LangGraph adoption — отложить; PoC за явными критериями входа

Статус: Accepted (Stage 6, 2026-11) · Дата пересмотра: при достижении
критериев входа (ниже) или изменении ограничений_stage.

## Context

Собственная оркестрация: линейный Atlas + ReAct-цикл (≤6 шагов) + линейный
Doc (см. ARCHITECTURE_AUDIT §1). Требование Stage 6 — оценить LangGraph без
переписывания. Проверено фактически: `langgraph 1.2.19` **транзитивно тянет
`langchain-core 1.7.4` + `langchain-protocol`** (проверено в чистом venv) —
прямое противоречие с ограничением «не добавляй LangChain».

## Ответы на 8 вопросов оценки

1. **Что LangGraph реально решает сейчас?** Durable-execution
   (checkpointing/resume) и формализация условных переходов вместо
   regex-классификатора `_COMPLEX_RE`. Обе проблемы сегодня не острые:
   воркфлоу короткие (15–75 s, измерено), живут в одном HTTP-запросе;
   misrouting регексом случается (найден в stage-1 e2e), но обходится
   дешевле, чем миграция графа.
2. **Что избыточно?** Subgraphs/мульти-агентные роутинги (у нас 2 линейных
   агента), streaming-модели LangGraph (SSE-контракт уже свой и запинен),
   built-in RetryPolicy (слои ретраев уже есть и выверены),Langfuse-интеграция
   «из коробки» (свой адаптер уже покрывает те же семантические точки).
3. **Нужен ли checkpointing?** Для текущего синхронного пути — нет: клиент
   отключился → перезапрос дешевле Resume. Становится нужным для
   **background jobs** (upload→embed, длинные аналитики) — там и проверять.
4. **Pause/resume, human-in-the-loop?** Продуктовых требований нет; SQL
   read-only под Guard. Планируемый сценарий «аналитик подтверждает SQL
   перед исполнением на production-источниках» — кандидат P3; тогда HITL
   LangGraph оправдан.
5. **Ошибки/повторы:** у LangGraph RetryPolicy на узлах; у нас —
   транспортные ретраи + parse-retry + SQL-repair + guard-запрет ретраев.
   Миграция с большой вероятностью ухудшила бы выверенную семантику
   (guard-ошибки НЕ ретраятся by design — в LangGraph это выражается
   нестандартно).
6. **Latency/сложность/тесты/observability:** latency — нейтрально
   (граф-оверлеи ~мс на фоне 15–75 s LLM); сложность и депграф — минус
   (5 новых пакетов, из них langchain-*); тесты — риск: 17 тестов цикла +
   e2e-контракт + **eval_sql_full импортирует `_generate_plan`/`_repair_plan`**
   — швы пришлось бы реэкспортировать; observability — паритет (наш адаптер
   уже на тех же точках, двойная инструментация — риск).
7. **SSE-контракт:** потребовался бы адаптер `astream_events` → наши
   `step`-события (id/title/tool/status/duration_ms) — реализуемо, но это
   ещё один слой + тесты соответствия.
8. **Совместимость с evaluation:** golden-наборы гоняют функции агентов
   напрямую; при миграции обязаны сохраниться: функции-швы, параметры
   генерации, хеш промпта в manifest. Langfuse-scores/datasets НЕ считаем
   заменой собственного контура (разные вопросы: прод-трейс vs методология).

## Decision

**Вариант A: сохранить текущую оркестрацию.** LangGraph не внедрять сейчас.
PoC допускается ТОЛЬКО при достижении критериев входа, и не на
request-пути, а на первом background-воркфлоу (upload-пайплайн).

**Критерии входа для PoC (любые два):**
1. фоновый воркфлоу с длительностью > 2 минут и требованием resume;
2. появился human-approval шаг (подтверждение SQL) в продукте;
3. ≥ 3 одновременных длинных джобов на воркера с приоритизацией/отменой.

## Alternatives

- **B. LangGraph на Atlas сейчас** — отвергнуто: противоречие с
  ограничением stage («no LangChain» — транзитивно нарушается), миграционный
  риск против нуля измеримой выгоды (проблемы бюджета шагов и cross_source
  LangGraph не решает).
- **B'. LangGraph только на Doc** — отвергнуто: Doc линеен, цикла нет.

## Consequences

- +0 новых зависимостей; eval/SSE/тесты стабильны.
- Regex-роутинг «сложный/простой» остаётся долгом (замена на
  LLM-классификатор или явный граф — отдельным маленьким изменением,
  без LangGraph).
- Durable-execution откладывается до background jobs (ADR-005), где
  checkpointing реализуем и собственно (шаги-статусы в jobs-таблице).

## Risks

- Собственная оркестрация — наш код = наша ответственность: бюджет шагов и
  parse-retry уже ловились тестами; новые фичи цикла требуют своих тестов.
- Если HitL понадобится раньше P2 — пересмотреть ADR.

## Migration strategy (если PoC состоится)

1. Новый воркфлоу (upload-pipeline) на LangGraph с `PostgresSaver`-
   checkpointer, thread_id = `{workspace}:{job_id}`; 2. Adapter
   SSE-событий не нужен (джоб-WS/SSE отдельно); 3. Оценка: латентность,
   resume после kill-9, изоляция thread_id между тенантами (см.
   SAAS_ARCHITECTURE §LangGraph×SaaS); 4. Только после успеха — обсуждение
   миграции Atlas.
