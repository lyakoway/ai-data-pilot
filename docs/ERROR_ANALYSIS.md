# ERROR ANALYSIS — типовые ошибки Text-to-SQL (все модели, v1+v2)

Источник: `scripts/error_analysis.py` по 6 merged-артефактам (5 моделей GLM,
golden v1+v2), 141 верифицированный провал (ambiguous-кейсы без проверки
корректности исключены; инфра-сбои выделены). Классификация — эвристика по
структурной разнице сгенерированного и эталонного SQL: метки направляющие,
финальная ручная проверка выборки обязательна для выводов о причинах.
Сырые данные: `backend/bench_results/sql_error_taxonomy_*.csv|json`.

## Распределение по типам (сумма по всем моделям и наборам)

| Тип | Случаев | Доля | Что это значит |
|---|---|---|---|

| **filter** | 39 | 27.7% | иной набор фильтров (is_partner, статус, страна, тариф) — модель опускает или добавляет условия |
| **wrong_table** | 30 | 21.3% | другой набор таблиц (лишняя/недостающая dim-таблица) |

| wrong_join | 4 | 2.8% | другое число/состав JOIN |
| interpretation | 2 | 1.4% | структура совпала, результат отличается (семантика/порядок) |
| infra | 1 | 0.7% | клиентский сбой (не качество модели) |
| no_sql | 1 | 0.7% | модель не вернула SQL |

Паттерн устойчив по моделям (см. `aggregate` в JSON): aggregation и filter
доминируют у ВСЕХ пяти моделей — включая лучшую glm-4.5-flash (6+6+2 в v1).

## Примеры (из CSV; сгенерированный SQL сокращён)

- **temporal / sql_020 (glm-4.5-flash, v1)**: «Сколько поездок за первую
  неделю апреля?» → модель написала `date('2024-04-01')` — **галлюцинация
  года**: в данных 2026. Класс ошибок «неверный литерал даты» не виден в
  структурной разнице типов — ловится только сравнением результатов.
- **aggregation / sql_014**: «Выручка по типам транспорта» → `SUM(revenue_rub)`
  без округления и без сравнимого набора колонок с эталоном.
- **wrong_table / sql_035**: «Пользователи >30 поездок» → лишние колонки из
  dim_user при совпадающем наборе таблиц — знаменатель Result Accuracy
  чувствителен к выбору колонок (ограничение методики, см. docs/EVALUATION.md).

## Категорийные выводы (из eval-артефактов)

- **join_complex = 0–30%** Result Accuracy у всех моделей на v1; 60% у
  4.5-flash на v2 — сложные JOIN остаются главной зоной риска.
- **temporal = 20–33%** на v2 (1/5 у лучшей модели) — вторая зона.
- simple/edge — 58–100%: базовые запросы отработаны.

## RAG (judge + retrieval, кратко)

- Retrieval: гибрид удерживает 100% Recall@1 на chunk-level наборе v2;
  bm25 и vector по отдельности теряют по одному кейсу на @1 (bm25 ведётся
  на лексическое совпадение «админк-» вместо семантики; vector путается в
  title-заглушке чанка #0 — очистка корпуса рекомендована).
- Генерация — **исправление этапа 4**: faith-числа этапа 3 (0.05, «2/4
  отказов») были артефактом бага инструмента: `rag_judge.context_of` читал
  несуществующий ключ `doc_id` (реальный — `id`), и judge получал ПУСТОЙ
  контекст. После фикса и A/B на идентичных условиях (одна сессия, один
  корпус, glm-4.5-flash): старый промпт «ПОДРОБНО» — faithfulness 0.75,
  abstention 3/4; новый контракт точности — **faithfulness 1.0, abstention
  4/4, citations 1.0**; relevancy 1.0 → 0.95 (единственная потеря — честный
  отказ, по рубрике это ожидаемо). Калибровка judge скачет 1/3–3/3 между
  прогонами — дельты надёжнее абсолютов; сильный judge остаётся P1-задачей.
