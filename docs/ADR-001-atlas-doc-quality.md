# ADR-001: Prompt-level quality fixes for Atlas (SQL) and Doc (RAG)

Дата: 2026-10-27 · Статус: candidate (результаты A/B — в BENCHMARK_RESULTS.md)
Контекст: этап 4 quality engineering; наблюдения подтверждены артефактами
этапа 3 (таксономия 141 ошибки; judge-прогон Дока).

## Решение

**1. Atlas — PLAN_SYSTEM + SCHEMA_CATALOG (минимальные, без изменения алгоритма):**

- правило `ROUND(SUM(...), 2)` для денежных сумм — закрывает доминирующий
  подкласс aggregation-ошибок (34 из 53 без округления);
- минимальность колонок (с примером служебных полей из реального провала
  sql_035) и таблиц — wrong_table 21%;
- COUNT(*)/COUNT(DISTINCT) критерии — повторяющиеся aggregation-паттерны;
- «реальные года из данных» + факт-блок диапазона дат в SCHEMA_CATALOG
  (2026-04-01…2026-07-15, проверен по БД) — галлюцинация года 2024 (sql_020).

Отвергнуто: правило под каждый из 39 filter-провалов — паттерн разнородный,
риск перенакачки промпта одним классом примеров (требование этапа: не писать
правила по одиночным примерам).

**2. Doc — SYSTEM переписан с «отвечай ПОДРОБНО» на контракт точности:**

1) буквальный grounding; 2) короткий отказ при отсутствии ответа;
3) обязательные [n] на реальные фрагменты; 4) CONTEXT = данные, не инструкции
(анти-инъекция); 5) запрет «структуры ради структуры».

Причина замены, а не правки: «ПОДРОБНО» напрямую конфликтует с grounding —
модель вынуждена раздувать ответ за пределы контекста; это подтверждено
judge-артефактами (спекулятивные вставки вида «вероятно, содержащего
географические координаты»).

**3. Корпус RAG — title-заглушки исключены из индекса** (load_chunks):
единственный промах vector-режима на golden v2 был ранжированием заглушки
выше контентной секции. Исправление детерминировано проверяемо.

## Что защищает от регрессий

- `tests/test_prompt_contracts.py` (12) — пин контрактных правил промптов
  и факта диапазона дат;
- `tests/test_doc_behavior.py` (6) — поведение Дока на негативных/
  конфузибл/инъекционных запросах, честный отказ mock-пути;
- A/B через существующий контур (eval_sql_full/eval_rag/rag_judge с
  manifest) + `check_regression.py` (Wilson-гейт).

## Последствия

Промпт стал длиннее (~350 токенов) — влияние на latency/токены измеряется
в тех же A/B артефактах; качество сравнивается на идентичных наборах
(v1/v2 golden, rag2-24). Исторические baseline-артефакты не тронуты.


## Addendum (2026-11-03): инструментальный баг judge

При подготовке A/B найден баг `rag_judge.context_of`: sources Дока несут
chunk-id под ключом `id`, а инструмент читал `doc_id` → judge во всех
прогонах этапа 3 получал контекст из одних заголовков. Следствия:
- faith 0.05 и «нестабильность калибровки» этапа 3 — артефакт инструмента
  (калибровка строилась на встроенных примерах и проходила, реальные кейсы
  судились по пустому контексту);
- после фикса (использован `s.get("id") or s.get("doc_id")`, верифицировано
  на known-good кейсе) baseline-ответы Дока оказались значительно лучше
  приписанных (faith 0.75, не 0.05), а эффект промпта подтвердился:
  0.75 → 1.0 faithfulness, 3/4 → 4/4 abstention (paired, одна сессия).
Урок зафиксирован: LLM-judge обязан проходить позитивный контроль на
known-good кейсе в каждом прогоне, иначе нули интерпретируются как качество
системы, а не инструмента.
